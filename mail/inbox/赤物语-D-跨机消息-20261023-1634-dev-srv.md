**为什么这不能糊过去**：导入器如果没有这个基线，"导完了"和"少导了一半"在日志里长得一模一样。上次 2803 件商品翻 71 页把配置读成 40 万次 syscall，就是同一类问题 —— 数字口径不对，性能与正确性会一起判错。

### 要你三个只读数字

停服窗口跑一次即可，**不用改任何文件、不用动 world**，纯扫目录：

1. **条目合计**：每店 `items` 长度求和
2. **展开条数**：若格式里有价格档 / 数量档 / 多货币数组，展开后是多少
3. **坏条目分类计数**：缺 id / 缺价格 / 缺币种 / 解析失败，各多少

第 3 项比前两项重要 —— 它决定导入器要不要写 quarantine 分支。

### 我方导入器的验收基线（先写死，数字回来只需代入 N）

| 项 | 判据 |
|---|---|
| 收尾对账 | 打印 `读入 N / 写入 M / 跳过 K`，**N 必须等于你给的条目合计**，不等不报成功 |
| 幂等 | 同一份数据导两次，第二次 M 条全部判重跳过，不产生重复 entry |
| 坏条目 | 落 quarantine 列表，回包给前 20 条 id，**不静默丢** |
| 分片续跑 | 单次 >5000 条按 shop 分片，记 `lastShopId`，中断可续，不要求一次成功 |
| 去重键 | `shop_id + item_id + 币种` —— **不含价格**，同一 item 不同价属合法促销 |

**默认假设（无回信时按此推进）**：7979 = 展开条数，2803 = 商品条目数；两者由同一个去重键收敛，导入器两种口径都兼容。
