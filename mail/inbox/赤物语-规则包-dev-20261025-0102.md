<NumberedList id="SJmlJGwIllnOYNDAsX88NI">
  <Mark bold>「读端截断」= 流错位，不是防御（3 次提及）</Mark>：`int n = Math.min(buf.readVarInt(), MAX); for(i<n) read()` 只读 MAX 条就转去读后面的字段 ⇒ 第 MAX+1 条被当成下一个字段解析，一路垃圾值且<Mark bold>不抛异常</Mark>，表现只是「界面数据全错」。唯一正确写法是「全部读完、只保留前 MAX 条」。判据：任何 `Math.min(...readVarInt...)` 上桌先问「剩下的谁读」；协议测试断言必须同时验「值相等」+「读完后无剩余字节」。<Mark bold>写端同样要截断</Mark>（第七轮补）：`PacketByteBuf.writeString(s, max)` 超限在<Mark bold>下发时</Mark>抛 EncoderException ⇒ 服务端每帧报错、客户端一个包都收不到（界面永远空白，探针 `recv=0`），而静态门 / 单测 / 编译全绿。写法固定 `s.length() <= max ? s : s.substring(0, max)`，上限按最长真实值留余量（路径 128 起），下发处 try/catch 打 `toString()`。

  <Mark bold>★交接/计划文档里「明天规则包会是 N 条 / hash=X」这类预测值，在每天都有增量的流水线里必然过期；计数类元数据的真源只有一个，下游只写判据不写预测值★</Mark>（2026-10-24 F 第 20 轮，同族连续 5 轮）：每轮 `_HANDOFF.md` 收尾都写「明日规则包直传 N 条 / hash X」，而 A/D 队列在夜里继续往 `_LESSONS.md` §一 追加硬坑 ⇒ 次日实际条数总比预测多（73→74→78→83→84→85→88→91→92→94→95，10 次里 10 次过期）。危害不是「发错包」（F 每轮重跑 `_hash.py` 才发现并修正），而是<Mark bold>下游读到旧数并据此下判断</Mark>：A 按「94 条」认为已同步、D 按旧 hash 认为「无变化」。定式：① 交接/计划里<Mark bold>只写判据</Mark>（「以 `_hash.py` 实算为准，发前重跑」），不写预测数值；② 必须写数值时前缀「截至 \<时间>」，并在同一句里写明「后续队列还会改写」；③ 与 #91 同根：<Mark bold>计数类元数据的真源只有一个</Mark>（哈希脚本的 entries/hash），文档里的任何副本都是缓存，<Mark bold>缓存不许当判据</Mark>。

<NumberedList id="5fRuRAUNuOtOvTqle6MtPp">
  <Mark bold>★「原文已保留」只是把证据留在盘上：不接上重解析与导回入口，就等于没恢复；而「绿报告」不绑定提交号，你验的就是改动前那棵树★</Mark>（2026-10-24 A 第 N+117 轮 · R201）：R198 把读不懂的离线挂账原文写进 `unreadable` 段，注释写着「等字段修好（或管理员照备份补录）后可恢复」。实际 `parseInto` 把每条原文<Mark bold>直接塞回</Mark> UNREADABLE、<Mark bold>从不重解析</Mark> ⇒ 字段改对、模组装回来，这笔钱也永远回不到 `entries`；玩家永远看到「请联系管理员」，管理员则没有任何入口（只能手改全服一张表，而正常条目和坏条目混在一起）。同轮还撞到第二件事：上一轮报告写 `test 561/0/3`，但那是在<Mark bold>改名之前</Mark>跑的，之后只跑了 `compileJava` ⇒ HEAD 上 `compileTestJava` 根本编不过（`RebuildStatus.UNREADABLE` → `SCAN_INCOMPLETE`，测试仍引用旧名），单测链静默失效一整轮。定式：① <Mark bold>「保留」与「恢复」是两件事</Mark>：写「可恢复」必须在同一轮给出「读盘重试 + 管理入口 + 端到端实机（钱真的进玩家余额）」三件，缺一件就是注释级修复；② <Mark bold>导出文件名不许复用损坏备份的前缀</Mark>（`FileRepair.state` 按 `stem.corrupt-*` 判状态，导出件撞前缀 ⇒ 状态永远 RECOVERED，玩家每次登录都被提示）；③ <Mark bold>导回要闭环</Mark>：坏条目也留原文、受每人上限、`save()` 失败逐笔回滚、`clear` 落盘失败把原文放回（#66 家族）；④ <Mark bold>清单里的「原因」实时重算</Mark>，不存第二份元数据 —— 两条平行表迟早错位；⑤ <Mark bold>绿报告必须绑定提交号</Mark>：`compileTestJava` 失败时 Gradle 的 `test` 任务直接跳过，报告里的 `N/0/3` 会是更早那棵树的数字 ⇒ 收尾一律「当前 HEAD 上 `./gradlew test --rerun-tasks`」并把 commit 写进报告；⑥ <Mark bold>闸门自检先自证</Mark>：本轮 `_e51` 首跑 11 个反样本只命中 7 个（R2 因日志行里也出现 `restored`、R3 因开头也有同一个 `return`、R4 因「已满」分支也 `add(el)`、R6 因票据命令的 `confirm` 同名）⇒ 判据要钉<Mark bold>分支位置</Mark>（catch 之后 / 连续两行 / 锚点之后 1200 字符），不能只判「文件里出现过」。
</NumberedList>

  <Mark bold>★「撤回/作废」类动作不是回一封信就完事：对方台账只认时间点，不认后来的解释——本方提前作废时必须把「作废时刻 + 节点」一起给出，否则历史会被写成「收到通知才撤」★</Mark>（2026-10-24 F 第 21 轮）：srv 21:24 来信要求「请 dev 视为已取消、撤回 1403 接单」，而本方在 <Mark bold>05:58</Mark>（早 15h26m）就因 Aki 移除 Origins 把台账 `cancelled`、停推并已发信告知 —— 两个时间点描述的是两件不同的事：前者是「接到通知才响应」，后者是「决策 → 台账 → 通知」的 4 小时闭环。若回信只写一句「好的已撤回」，对方台账（我方无写权限）就会把作废时间记成 21:24，<Mark bold>把一次有效的机制运行记成一次迟钝的补票</Mark>，而且以后无法从台账反推真实原因。定式：① 这类回信必须给<Mark bold>时刻表</Mark>，每行带「时间 + 动作 + 节点 id」（发出需求 → 本方接单 → <Mark bold>本方作废</Mark> → 对方确认），并明确本封是<Mark bold>确认</Mark>还是<Mark bold>执行</Mark>；② 撤回必须落到<Mark bold>唯一台账</Mark>（本项目 `_MOD_FEATURES.json` 的 status），写信、口头、规划文档划掉都不算；③ 对方台账不在你写入范围时，<Mark bold>只请求它记时间点</Mark>，绝不要求它改文件（本项目 srv 对 `_srv_REQUESTS.md` 只读）；④ 措辞要能自证：写「请在你自己那侧记一笔」，不要写「请把台账标 cancelled」——后者读起来像越界指令，会让对方回一封长信解释权限边界。
</NumberedList>

<NumberedList id="7QTkxtp7miK8YJIYMP9HYR">
  <Mark bold>★「留证」的段位一旦设上限，超出部分必须换个地方继续留原文；而「证据文件」跨进程必须复用最近一份，否则命令面指向的那份只是半份★</Mark>（2026-10-24 A 第 N+118 轮，R202）：`pay_pending.json` 的 `entries` 有「每人 200 笔」上限，`unreadable`（读不懂的原文）一条都没有 —— 同一张表两套尺度，于是一份坏掉的大文件或反复导入坏清单就能把它撑到任意长度；而 `load()` 的条件是「段非空就归一化」，等于<Mark bold>每次都把整份钱表全量重写一遍</Mark>（内容一个字没变也写）。改法不是「满了丢最老的」（那正是我们连续修了五轮的病：把「留了原文」变成「没有原文」），而是① 唯一入口 `keepRaw()`：未满就收，满了<Mark bold>追加</Mark>到 `.unreadable-overflow-<epoch>.jsonl`（APPEND 一行一条，仍可 `import` 导回），转存失败时<Mark bold>宁可突破上限也留在内存</Mark>（不丢 > 体积）；② 溢出文件名前缀<Mark bold>不许撞 `corrupt`</Mark>（撞了 `FileRepair.state` 会把状态永远判成「已修复」，R201 同一个坑）；③ 归一化改成变更判定（比较「盘上那段」与「内存里这段」，不同才写）。★探针打出来的第二个坑★：`overflowFile` 是<Mark bold>进程内</Mark>字段，重启后归零 ⇒ 又建一份新文件，而 `/rt admin pay` 打印的是新名字、管理员按它 `import` 只能导回<Mark bold>这一轮</Mark>那几条（旧文件里的钱还在，但命令面点不到）⇒ 首次溢出必须先扫盘复用最近一份。★定式★：① 给「证据/隔离」类集合加上限时，先回答「超出那条去哪」，答不出来就不许加；② 溢出文件必须与主文件<Mark bold>同一套导回入口</Mark>（这里是 `entriesOf` 的 JSONL 兜底，且一行坏就整份拒绝）；③ 任何「本次运行新建的文件名」都要问一句「重启后还找得到吗」，找不到就改成扫盘取最新；④ 上限值要让玩家/管理员<Mark bold>看得见</Mark>（`N/上限`），否则 200 与 20000 对人是同一句话。
</NumberedList>

<NumberedList id="esQnKgAETbRdTJtXWH1xBg">
  <Mark bold>★「可导回的证据文件」= 一份可重复执行的付款清单：导回成功必须当场消费掉来源（改名），否则第二次导回就是重复发钱★</Mark>（2026-10-24 A 第 N+119 轮，R203）：R202 把溢出的原文存成 `.unreadable-overflow-<epoch>.jsonl` 并允许 `/rt admin pay import` 导回 —— 但 `import` 只把原文搬进挂账队列，<Mark bold>来源文件一个字节都不动</Mark>，而 `latestOverflow()` 下次溢出时还会<Mark bold>复用同一份</Mark>继续追加。于是「已处理」和「待处理」在盘上长得一模一样：① 同一份文件能再 import 一次，里面每一行都是一笔真实转账 ⇒ 已付过的钱再付一遍，没有任何东西会拦；② `clear confirm` 只清主文件 `unreadable` 段，溢出文件永远挂在「待处理」，玩家提示里的数字<Mark bold>永远不归零</Mark>（处理完了还在报「有 N 笔读不懂」）；③ 导回过程中新读不懂的原文会经 `keepRaw→spill` <Mark bold>追加回正在读的那份文件</Mark>，跟着归档一起「消失」在已处理文件里，连计数都少算。三处同修：归档（`Files.move` 改名，<Mark bold>字节一字不动</Mark>，`imported` / `archived` 两个 tag 区分来历）、<Mark bold>先落盘再消费来源</Mark>（顺序反了就是「文件没了、钱没进表」）、`spill()` 在 `importing` 期间换一份新文件；计数改<Mark bold>读盘</Mark>（`overflowFiles()`）而不是回内存 `overflowed`。★定式★：① 任何「能被重新执行一次来恢复数据」的入口，都要问「第二次执行的后果是什么」，涉钱的一律<Mark bold>执行成功即消费来源</Mark>；② 「处理完了数字要消失」和「处理完了文件要留着」是两个需求，用<Mark bold>改名</Mark>同时满足（删=最贵的错，留着原文件名=可重复执行）；③ 进程内计数器只配当日志节流，<Mark bold>凡是给玩家/管理员看的数字都从盘上算</Mark>（重启归零的计数会让「已解决」看起来「还在出事」）；④ 导入/批处理期间往「同一个目录里的同一族文件」写东西，必须先排除「正在被读的那一份」。

<NumberedList id="AppxHcw0UPek9DC5rdu7DW">
  <Mark bold>★「超时/到期」类规则如果只在定时扫描里执行，就等于没执行：窗口期里做那件事的入口必须自己判截止，而且截止只能有一个来源★</Mark>（2026-10-25 A 第 N+120 轮，R204）：R181 给「接单」补了到期判据，理由写得很清楚——「扫描每 30 秒才跑一次，中间这段窗口没人挡」。但同一族的另一半漏了：`deliver()` 只判「状态 ACCEPTED + 是我接的」，<Mark bold>不看接单截止</Mark>。于是过了宽限期、状态还停在 ACCEPTED 的那段（最多 30 秒；扫描卡住/被关掉就是无限期）里，交付照样成功：赏金照发、物品照收、人也不会被拉黑，「接单超时」这条规则可绕过。实机反证：同一份夹具（超时 10 分钟的 ACCEPTED）在新 jar 上被拒（余额 1000→1000、物品还在、状态仍 ACCEPTED），在旧 jar 上<Mark bold>交付成功</Mark>（1000→1100、物品消失、状态 DONE）——「修好了」和「探针能看见修好了」是两件事，`--jar old` 反证必须在同一份夹具上跑。同轮打出的两个同族假绿：① 协议里的 `remainMin` / `deliverRemainMin` 是<Mark bold>打包那一刻的死数</Mark>，Hub 只在「打开/刷新/动作回包」取快照 ⇒ 停留十分钟还写着十分钟前的数（倒计时根本不会走）；② 过期但还没被扫描回收的 OPEN 单渲染成「剩 0 分」并照常给可点按钮（0 与「已失效」撞值，硬坑 #74 的另一半）。★定式★：① 写任何「到期/超时/限额」规则，先列「谁会在窗口期里执行这个动作」，<Mark bold>逐个入口加判据</Mark>，只放定时器里就等于没有；② 同一个截止只允许一个纯函数（`acceptDeadline`），扫描 / 执行入口 / 界面 / 命令四方全从它取，比较符也必须同源（`>=` vs `>` 差一毫秒就会出现「界面说超时、扫描还没动手」）；③ 倒计时类展示<Mark bold>发 deadline 不发 remaining</Mark>，客户端只用「本地流逝」算（`deadline - sentAt - (now - receivedAt)`，两端时钟差在 `sentAt` 上抵消，别指望对时）；④ 「拒绝」与「结算」必须分开：交付入口只拒、不在这里放回/拉黑，否则与扫描双写；⑤ 旧闸门撞上新设计时改判据要钉<Mark bold>语义</Mark>（「新字段只能追加」「分钟必须来自纯函数」）而不是钉方法名 —— 本轮 `_e37` R8 / `_e42` R5+R8 三处就是这么改的，改完 self-test 仍 7/7、9/9。
