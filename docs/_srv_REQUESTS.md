# _srv_REQUESTS.md — S4 → 开发端（dev）的需求台账

> **归属**：S4·发展规划 唯一写入。S3 只读（`python mail_scan.py req --pending` 取待发的去发）。
> **为什么有这个文件**（Aki 2026-10-23 定）：S4 的规划里会不断冒出「需要一个物品 / 一段 KubeJS / 一章任务 / 一张贴图」，
> 这些事只能在开发机做。以前这些需求只埋在规划正文里，dev 端看不见，Aki 也没法提前判断值不值得做。
> 现在一条需求一张单，走跨机信箱，回执带 REQ 号回来，闭环。
>
> **这个文件解决的是"规划 ↔ 制作"之间的断层，不是"写信"问题。**
> 信件有 3 种（事务/规则包/闲聊），都是**说完就完**；需求单是**有状态、要跟踪到交付**的第四种。

---

## 格式（写单必读）

一张需求单 = 一个 `### REQ-Nxx · 标题` 块，字段行固定这六个键：

- 状态: 草案
- 优先级: P0 阻塞开服 / P1 开服前想要 / P2 有余力
- 类型: 物品 / 方块 / 配方 / 任务 / 命令与权限 / 系统 / 美术 / 配置
- 关联: 规划出处（便于回查"为什么需要"）
- 发出: `-`（S3 发出后由 S4 回填日期）
- 回执: `-`（dev 回信后填文件名）

状态机：

```
草案 ──→ 待发 ──→ 已发出 ──→ 已接单 ──→ 已交付 ──→ 已验证
  │        │                    │
  └────────┴────────────────────┴──→ 已否决 / 已搁置 / 待重估（写明原因）
```

- **已否决** = 做不了或不该做，结案。
- **已搁置** = 能做但暂时不做，等条件。
- **待重估** = 前提变了，这张单可能整条不需要了。**与"已搁置"不同：搁置是等，待重估是重新判断要不要。**

正文固定七段，缺一段就是废单：

**1. 要什么**（一句，能让人立刻知道要做什么东西）
**2. 为什么现在要**（指向规划哪一节，缺了它哪个玩法不成立）
**3. 验收方式**（可执行、可观察；不写"体验更好"这种没法验的话）
**4. 已知约束**（1.21.1 NeoForge / 228 mods / KubeJS 现状 / 不能加新 mod 时怎么办）
**5. Aki 要做的动作**（具体到文件或命令，不要写"你看着办"）
**6. 兜底方案**（做不了的话退到哪一步 —— 有兜底的需求才敢接）
**7. 不要做什么**（防止过度实现。**这一段最省时间**）

硬规则：

- 一张单只说一件事。两件事拆两张。
- 正文 **≤ 40 行**。超过说明还没想清楚，先想清楚再发。
- 不写价格、不写档位、不替 Aki 决定商业化细节。
- 需求单也是信，走同一个信箱；文件名只带时间不带 REQ 号（保持可排序），
  REQ 号在正文首部与 `sentReqs` 里对应，S3 发完调 `mail_scan.py req --mark REQ-Nxx` 登记。
- **回执由 dev 用「跨机消息」回，标题或主题里必须带 REQ 号**，否则这条需求就断了。
